# Database design review — 2026-10-30

This records the earlier database snapshot. The later job-test review in [SUBMISSION_REVIEW.md](SUBMISSION_REVIEW.md) adds a reproducible SQL/migration/live schema comparison: column/constraint structure matches, but all 12 application tables differ in collation. That later review also updates the observed invoice count and submission priorities. Recommendations below remain unapplied.

Reviewed every column in the canonical schema, migrations, the live MySQL 8.0.30 schema, and the application code that reads/writes it. Recommendations below are **review findings**, not migrations applied in this change. The only requested schema change applied is removal of `invoice_counters` through migration 014.

## Observed integrity

The inspected database contained 3 invoices and 5 invoice items. Header totals, item totals, discount bounds and cancellation actor/time presence passed the read-only consistency checks. However, all 3 cancellation timestamps are earlier than their creation timestamps; the time-zone finding below explains the risk. There were no inventory movement records. This small sample is not proof that future invalid writes or concurrent requests are covered.

Good foundations: InnoDB transactions, consistent unsigned foreign-key IDs, a unique invoice number, a unique warehouse/product inventory pair, nullable unique customer contacts, decimal money, product snapshots, and foreign-key protection against orphan records. These choices should be retained.

## Priority findings

| Priority | Finding | Suggested improvement — not applied |
|---|---|---|
| High | `inventory_movements` only records manual adjustments. Invoice creation and cancellation change stock without adding movements. | Record every stock change in the same transaction, with an invoice/reference ID and movement type. Define a starting balance so the ledger can reconcile with `inventory.quantity`. |
| High | `inventory.quantity` and item quantities are integers, but the product unit catalogue includes kilograms, litres and metres. | Decide whether measured products can have fractions. If so, use an agreed decimal quantity precision across inventory, invoice items, movements, services and validation. Do not change only one column. |
| High | `quantity_change` is signed `INT`; stock balances are unsigned `INT`. A valid balance change can exceed the signed range. | Align ranges, for example a signed `BIGINT` delta with bounded unsigned balances, or consistent decimal quantities if fractional stock is required. |
| High | Monetary checks only require non-negative values. They do not enforce header/item arithmetic or maximum discounts. | Add checks for `discount_amount <= subtotal`, `total = subtotal - discount_amount`, and corresponding item arithmetic, with the agreed rounding rule. Application checks remain necessary. |
| High | An invoice references mutable customer information instead of snapshotting the customer's name/contact/address. | Snapshot the billing identity when issuing the invoice. Otherwise editing a customer changes what an old invoice displays. The new details UI displays current customer metadata; this change does not add snapshots. |
| High | `DECIMAL(12,2)` allows at most 9,999,999,999.99, but quantity × price and aggregate totals are not bounded before inserts. | Validate all money results against storage limits before writing. Decide whether that maximum fits the product scope before widening precision. |
| Medium | No check connects `status='cancelled'` to non-null cancellation actor/time. | Add a cancellation-state consistency check and retain cancellation as an audited state transition rather than deleting invoices. |
| Medium | Movements do not enforce `quantity_after = quantity_before + quantity_change`, sign rules, or required reasons. | Add arithmetic/type checks and require reasons for manual additions/removals. Ensure application transactions roll back if the movement insert fails. |
| Medium | A product code stays globally unique after soft deletion, but the application's duplicate check excludes deleted rows. | Choose a policy. Keeping codes permanently reserved is simplest; then include deleted records in the duplicate check. Allowing reuse requires a deliberate schema strategy. |
| Medium | Invoice items store a discount amount, but not the entered percentage. Header discount combines line discounts and any invoice-level discount. | If exact discount reconstruction is required, snapshot the entered line percentage and separate invoice-level discount information. Amounts remain the accounting authority. |
| Medium | Invoice items snapshot English `unit`, but not its Arabic label. | Add an Arabic unit snapshot if historic bilingual documents must remain independent of future catalogue translations. Product name/code/price snapshots are already correct. |
| Medium | Invoice cancellation rows do not store a reason. General catalogue/user/warehouse edits also lack an audit trail. | Add audit data where the product's accountability requirements justify it, rather than adding unused `created_by` fields everywhere. |
| High | Live database time zone is `SYSTEM` / Arab Standard Time, while CLI PHP defaults to UTC and the app has no explicit time-zone policy. All 3 inspected cancellations are timestamped before creation. | Choose UTC storage with UI conversion, or consistently configure Asia/Riyadh. This matters for dated invoice numbers and cancellation timestamps near midnight. |
| Medium | `idx_products_search_code(code)` duplicates `uq_products_code(code)`. | Remove the redundant non-unique index in a separate measured migration. A leading-wildcard `LIKE '%term%'` also cannot use a normal B-tree range lookup, so a name index alone does not solve substring search. |
| Medium | Login expiry cleanup filters only on `attempted_at`, while the existing index starts with `ip_address`. | Add an expiry-oriented time index if needed at scale; use scheduled retention cleanup rather than deleting old attempts on every login. Keep the current IP/time index for per-IP limits. |
| Medium | Phone uniqueness depends on a weak normalization rule. Equivalent local/international formats can remain different strings. | Define a canonical phone representation and validate before storage. Keep missing values as `NULL`; nullable uniqueness is appropriate. |
| Medium | Existing sessions have no user reference/version for targeted invalidation; permissions live in a session snapshot. | Refresh authorization per request or introduce an authentication/session version. A deactivated or reassigned user must not keep outdated access until logout. |
| Medium | Invoice numbers are unique, but requests have no idempotency key. A retried save can create a second valid invoice with a different number. | If reliable retries are required, store a unique client request key and return the previously created invoice for repeats. Disabling the Save button alone cannot enforce this invariant. |
| Medium | Foreign keys enforce existence, not active status. Warehouse/product activity checks can race with deactivation. | Define whether an already-started sale may finish. If it must not, lock/recheck activity inside the same transaction and make deactivation follow compatible locking. |
| Medium | Invoice items do not guarantee that their warehouse/product inventory row will still exist during cancellation. | Keep inventory rows once used, or make restoration explicitly handle missing rows. Currently an update affecting zero stock rows is not verified before cancellation is marked complete. |

| `warehouses` | `id`, `name`, `name_ar`, `address`, `status`, `created_at`, `updated_at` | Active/inactive state preserves history. A stable unique warehouse code may be useful; forcing display names to be unique is a business choice. No address history is retained. |

| `login_attempts` | `id`, `ip_address`, `attempted_at` | IPv4/IPv6 length is sufficient. IP/time index is useful; retention, global expiry lookup and account-based abuse controls need an explicit policy. |

| `customers` | `id`, `name`, `phone`, `email`, `address`, `created_by`, `created_at`, `updated_at` | Nullable unique contacts are appropriate. Improve canonical normalization and invoice billing snapshots. Define deactivation/deletion policy before adding customer deletion. |
| `invoices` | `id`, `invoice_number`, `warehouse_id`, `customer_id`, `created_by`, `status`, `subtotal`, `discount_amount`, `total`, `cancelled_at`, `cancelled_by`, `created_at`, `updated_at` | Keep stored totals as document snapshots. Add arithmetic/state checks and billing identity snapshots. Existing warehouse/date and customer/date indexes support scoped queries; assess an independent date index for global reports using actual plans. |
| `invoice_items` | `id`, `invoice_id`, `product_id`, `product_code`, `product_name`, `product_name_ar`, `unit`, `quantity`, `unit_price`, `discount_amount`, `line_total` | Product snapshots are intentional denormalization and should remain. Add precision/bounds/arithmetic checks and missing bilingual unit/discount metadata if required. A unique invoice/product key is appropriate only while one aggregated line per product remains the rule. |
| `inventory_movements` | `id`, `warehouse_id`, `product_id`, `movement_type`, `quantity_before`, `quantity_change`, `quantity_after`, `reason`, `created_by`, `created_at` | Expand into a complete ledger with references and compatible ranges. ## Counter removal and replacement

- `InvoiceRepository::nextNumber()` now queries the maximum numeric suffix matching the current prefix/date. Cancelled invoices remain included. Daily `0001` formatting and the unique invoice-number index are retained.
- `BaseRepository::withAdvisoryLock()` is the reusable repository locking function. `InvoiceRepository::numberedTransaction()` acquires the database-scoped lock **before** opening the invoice transaction and releases it **after** commit or rollback. Unlocked calls to `nextNumber()` are rejected.
- All invoice creation paths, including demo seeding, use `InvoiceService` and therefore this wrapper. Cancellation does not allocate numbers and continues using its existing row locks.
- Migration 014 drops the counter table; fresh `database/schema.sql` omits it. Historical migration 009 is retained so existing migration histories are not rewritten. Its rollback counterpart can reconstruct the old high-water marks from retained invoices.
- A plain `COUNT(*) + 1` is unsuitable: gaps cause reuse and concurrent requests can compute the same number. `MAX + 1` also needs synchronization; the query alone is not a reservation.
- Tradeoffs: this serializes cooperating invoice creation transactions on one MySQL server and scans that day's matching numbers. All writers must follow the same locking protocol. It is not a multi-primary distributed allocator. Keep issued/cancelled invoices; physically deleting the highest number permits reuse when the sequence is derived from retained data.
- The old counter row was a reasonable, efficient design for high daily volume. Removing it simplifies the schema, but is not inherently a normalization or correctness improvement.

Verified with the canonical fresh-install schema and four independent MySQL connections in an isolated temporary database: simultaneous full invoice saves, stock/item writes, cancelled numbers, suffix gaps, `9999` rollover, rollback, cancellation restoration and lock cleanup. The temporary database was removed. Existing application invoice records were not renumbered.
